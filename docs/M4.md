# LAML M4: deferred streams, value validation and a broader catalog

Status: implemented on the local branch `m4-deferred-validation` (off `main` 49c0748), host-tested. **Not pushed, not merged**: the owner asked for review before any integration or publication (decision of 2026-11-02, card `levrt-m4`). M4 instantiates no control, renders nothing, has no visual tree, and does not touch the shell, Explorer or LevRT.

## What exists

| Piece | Files | Purpose |
|---|---|---|
| Deferred stream links | `src/tree/logical_tree.{h,cpp}` (extended) | a stream after the first is tied to the node of an earlier stream that references it; the placeholder "object of another stream" now points at the node it stands for |

The XBF layer (M1), the M2 catalog behaviour and the M3 tree semantics are unchanged except where this file says so.

## Requirement by requirement (owner conditions)

1. **Resolve deferred streams and references respecting the documented XBF format.** `SetDeferredProperty` (a template or resource body) and `SetCustomRuntimeData` (content tokenised by a runtime-data payload) name a later stream. The tree records, per stream, `link = {fromStream, node, via, property}` and, per node, the streams it references (`linkedStreams`). A stream that continues a scope of its parent (its first operation acts on an object that is not in it) gets a placeholder whose `contextNode` is the object it stands for: the referencing node's parent when that node is a member (`PushScopeGetValue`) of an object, else the node itself. In `XbfVsmTest.v2.1.xbf` all 6 deferred streams are reached (3 by runtime data, 3 by deferred property) and the 3 scope continuations are linked; the dump shows each stream under the node that references it. Reference discipline: a reference must point to a *later* stream (self, backward and missing targets), and a stream may be referenced once (the second reference is dropped); each case is a `MalformedStructure` diagnostic, so `ok()` is false. A stream nobody references is counted (`orphanStreams`) and keeps its placeholder, reported as not linked. Not done: the *tokens* inside the runtime-data payloads (offsets into the deferred stream) are not used to place the subtree inside the parent's collection; the link is at the level of the referencing node.
2. **Validation of values, enums and properties, separating format errors, unknown references and unimplemented features.** `Validate()` gives each assignment and each collection item exactly one outcome: *valid* (a check was made and passed), *FormatError*, *UnknownReference* or *NotImplemented*; the worst of its findings wins. Findings and their meaning are in `validate.h`. Checks made:
   - a boolean, floating-point, integer, string, null, thickness, grid-length, colour or enum constant against the property's value type (an integer widens to Single/Double; integers are range-checked for Int16..UInt64/Byte; null needs a nullable, reference or String/Object type);
   - an enum constant against the property's enum (same enum, and the number is a member, or - for a flags enum - any OR of members);
   - an instance property used on an object that does not derive from the declaring type; a constant or resource given to a read-only property; an object assigned to a property whose value type it does not derive from;
   - a colour constant on a `Brush`/`SolidColorBrush` property is accepted (the public Brush page documents the colour syntax for Brush properties, and the real fixture `SampleWithChecksum.xbf` does this).
   Unknown references: property, object type or value type not in the catalog. Not implemented: resource references (never looked up), markup extensions, template bindings, type-converted text, deferred values, strings given to struct/class-typed properties (no converter is run), enums whose numbers the catalog does not declare, and every collection item (the catalog does not record element types).
3. **Catalog grown from verifiable public documentation, with source traceability.** `data/winui-api.types` is *generated* by `tools/catalog/idl_extract.py` from four MIT-licensed IDL files of microsoft-ui-xaml at the pinned commit `8da148dc...` (sha256 of the inputs in PROVENANCE.md). It carries one `source winui-idl <url at the commit> <commit> MIT` record and every type states `src=winui-idl`; a test fails if any type lacks a declared source. Facts only (names, base types, content property, property names and value types, enum members and numbers); no code or text beyond names. Cross-checks against the public Learn pages (retrieved 2026-11-02): BindingMode OneWay 1, OneTime 2, TwoWay 3 (test `TestApiCatalog`), ToggleButton.IsChecked / IsThreeState and base ButtonBase, the Brush colour syntax. The generator output is deterministic (re-run gives the same sha256) and reports what it left out.
4. **SampleXbf2 as regression, and the count after M4.** *67 objects. M3 (25-type seed): 3 types resolved. M4 (`winui-api.types`): 44 of 67 resolved* (properties: 98 -> 194 of 216). The other 23 objects are `Numbers.Controls.CalculatorButton` (22) and `Numbers.NumbersAndOperatorsEnum` (1): types the page itself declares in its own type table, which no public document describes, so they stay `UnknownType` on purpose (22 properties of CalculatorButton likewise). By distinct type: 7 of 9. The other fixtures with the new catalog, counted as resolved type references (not only objects): `XbfVsmTest.v2.1.xbf` 85 of 85 (82 objects), `PageWithConditionalXaml.xbf` 6 of 10 (the 4 unresolved are the predicate types of its conditional scopes), `CustomTypesPage.xbf` 9 of 11, `SampleWithChecksum.xbf` 1 of 1. Both numbers are asserted in `m4_tests` (the seed baseline 3/67 too), so a regression in either direction fails the build.
5. **Logical tree independent of the renderer and the window system.** Unchanged: `laml_tree` links `laml_types` and `laml_xbf` only; validation reads the tree and the catalog and creates nothing.
6. **No fictitious implementations to raise coverage.** The catalog is extracted, not typed in; a type outside the IDL files (`Windows.Foundation.Point`, `Windows.UI.Color`, ...) is **not** declared and stays unresolved (listed as catalog warnings); the page's own types are not added; the content property `FrameworkTemplate.Template` (XAML-only, not an IDL member) was left out by the generator and reported. Stable-table coverage of the catalog: 533 of 851 live types, 1584 of 1943 live properties (the seed had 21 properties).
7. **Negative tests, read limits, safe handling of malformed XBF.** Catalog text: undeclared/duplicate source, missing fields, mixed numbered/unnumbered enum values, bad/overflowing numbers (int64 limits both ways), flags on a non-enum, source-count limit, frozen catalog. Links: self, backward, missing and duplicate references, orphan. Validation: every finding code has a test and a clean counterpart; finding cap keeps the counts exact. Malformed input: 1,800 deterministic mutations (1-4 byte edits, truncations) of three real files are parsed, decoded, folded and validated (1286 survive the container parser); the tree stays consistent (parents, contexts and links in range, links point forward) and the outcomes always add up. The whole of `m4_tests` and `tree_tests` was also run under AddressSanitizer + UndefinedBehaviorSanitizer (`-fno-sanitize-recover=undefined`) with no report.

## Outcomes and counts

`TreeCounts` gains `linkedStreams`, `linkedContexts`, `orphanStreams`. `ValidationCounts` has one outcome per assignment/item plus `byCode`. Example, `SampleXbf2.xbf` with the new catalog: 216 assignments = 86 valid + 0 format errors + 98 unknown reference (almost all on `CalculatorButton`) + 32 not implemented; 40 items, all not implemented (no element types).

## Known limits

1. No file in the repository is *invalid*: all real fixtures are Microsoft test files and validate with 0 format errors, so the format-error paths are exercised by synthetic streams and mutated files, not by a real faulty file. A false positive on a real-world file is possible: the rules above came from the fixtures and the public pages, and only the Brush/colour case needed a correction.
2. Value types outside the IDL (`Windows.UI.Color`, `Point`, `Rect`, `TimeSpan`, `Uri`, `IVector<T>` ...) are unresolved: constants for them are only name-matched for Thickness, GridLength and Color; otherwise `UnknownReference`.
3. Collection element types and attached-property target types are not in the catalog; items and attached applicability are not checked.
4. Enum numbers are the IDL's (explicit or implicit ordinal, verified against the Learn BindingMode page for one enum); `[flags]` enums accept any OR of members. Enum text (type-converted names) is not parsed.
5. The IDL says nothing about which XAML-only members exist (`FrameworkTemplate.Template`, `VisualStateManager.VisualStateGroups`, `Storyboard.TargetName` ...), so they stay unknown properties.
6. Stable index tables remain tied to the pinned WinUI commit; the catalog is the same commit's IDL.
7. Runtime-data payload tokens are not followed; the subtree of a deferred stream is attached at the referencing node, not placed in the parent's collection.
8. Host tests only (Release and an ASan/UBSan Debug build, clang from the RosBE `20261015` toolchain); nothing runs inside LiberNT.

## Regenerating the catalog

    python -I tools/catalog/idl_extract.py 8da148dcd8ed65ea8b8ae664fbe45c9cc82e372b data/winui-api.types \
        <idl>/microsoft.ui.xaml.controls.controls.idl <idl>/microsoft.ui.xaml.controls.controls2.idl \
        <idl>/microsoft.ui.xaml.coretypes.idl <idl>/microsoft.ui.xaml.coretypes2.idl

where `<idl>` holds the four files from `dxaml/xcp/dxaml/idl/winrt/{controls,core}/` of microsoft-ui-xaml at that commit.
